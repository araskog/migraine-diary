# Production releases

The Production release workflow runs after successful push checks on main. It checks out the tested commit, serializes releases, runs Django migrations with a direct TLS-verified Neon connection, verifies no migrations remain, then deploys the API to Vercel. Failures stop deployment. Pull requests and preview branches never run this workflow against production. Only backward-compatible migrations belong in this flow; destructive changes need a separate rollout plan.

Before merging/enabling this workflow, create the GitHub `production` environment and add environment secrets `DATABASE_URL_UNPOOLED`, `VERCEL_TOKEN`, `VERCEL_ORG_ID`, and `VERCEL_PROJECT_ID`. Use the existing production project and direct Neon connection, never a preview database or pooled hostname. Restrict the environment to main. Secrets must never be committed. Without these secrets the job deliberately fails before changing the database.

Vercel must use backend as its root directory so backend/vercel.json disables competing automatic main deployments. Verify that setting in the dashboard before the first release. Preview deployment integration remains enabled. The CLI deploys the checked-out backend directly; it uses the production project identified by the environment secrets. Cloudflare's existing frontend deployment remains independent: keep frontend/API contracts backward-compatible.

An authenticated operator must verify the first release, including login and diary access, and confirm that no production API is released through a second path. The workflow_dispatch action retries a release from main; it is not a rollback mechanism. Database rollback is never automatic.

Guidance checked: [Django migrations](https://docs.djangoproject.com/en/5.2/topics/migrations/), [Vercel Git configuration](https://vercel.com/docs/project-configuration/git-configuration), and [Vercel CLI deploy](https://vercel.com/docs/cli/deploy). Running migrations in a serialized release job, instead of a preview/build or request handler, prevents preview writes and concurrent migration jobs. Hosted secret configuration and first-release verification remain operational work; repository tests do not prove them.
